Intake creates tasks from matching requests. The Backlog automation refines those tasks in SuperPlane and records a plan and assessment. Use the task's refinement conversation to add context before starting implementation. The canvas examples below illustrate workflow design and can differ from the current default template.

## Decide what enters the backlog

Start with the event that represents work for your team. GitHub issues are a common source but a custom Factory can listen to another source-control system, issue tracker, webhook or manual task.

Filter early when the source contains work the Factory should never consider. Repository, project, label and issue state are reliable routing signals. Keep product judgment in the source process instead of asking an agent to infer whether every issue belongs in scope.

Browse [source control and work intake](/integrations/source-control) for supported issue and repository services.

## Give the analysis enough context

The analysis agent should receive the task description and the repository context needed to assess it. Ask for a structured result that downstream nodes can use. Useful fields include:

- a short statement of the requested outcome
- the likely code area or repository
- missing information that blocks implementation
- a confidence result with a brief reason
- a recommendation to start or ask for clarification

Avoid sending an entire repository or unrelated issue history into every scoring run. A smaller input reduces cost and makes the reason for the result easier to inspect.

## Route every result deliberately

The illustrated canvas uses separate routes after the agent:

- **Passed:** Attach the analysis as a task artifact and report the confidence check.
- **Failed:** Record the run error so the task shows why analysis did not finish.

Keep low-confidence tasks in Backlog for refinement. A person can clarify the task in SuperPlane, narrow its scope or reject it. Update the source issue when those decisions also belong in the issue tracker.

## Keep the start decision visible

Scoring helps assess readiness; it does not guarantee success or automatically start every high-scoring task. **Auto-start** is off by default. Enable it in Planning only when you want tasks that meet its readiness conditions to start without manual **Start**. Keep intake filters and start settings separate.

Automatic start requires a task specification, no outstanding refinement questions, and maximum first-reported Clarity, Complexity and Verifiability scores. A later high score does not override a low first score for automatic start. Review and start such a task manually when it is ready.

## Control backlog cost

Backlog refinement can run for new tasks and further conversation turns, so intake volume and repeated refinement affect cost.

- Filter unsupported work before an agent node.
- Use a smaller model for classification when it produces a reliable structured result.
- Limit the repository context to files and metadata needed for scoring.
- Do not rerun analysis until the task or its context changes.
- Record the reason for rejection so a person can fix the request without another exploratory run.

Once the task is approved, [Implement automation](/fundamentals/automation-implement) controls the code work.
