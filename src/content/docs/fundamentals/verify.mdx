Verify is where you review the attached pull request and its evidence against the task. The default GitHub setup includes Merge confidence and a discussion-feedback handler. It does not install every check or repair workflow described below.

## Build an evidence stack

No single signal proves every kind of software change. Choose evidence that matches the task's risk. The following are possible verification inputs, not a list of installed default gates.

| Evidence | What it can establish |
| --- | --- |
| **Repository checks** | The change passes tests, type checks, linting and build rules enforced by the project |
| **Pull request state** | The branch is current, the expected files changed and required review policies are satisfied |
| **Task-specific checks** | The behavior requested in the issue can be observed or reproduced |
| **Agent review** | The diff can be inspected for omissions, unintended scope and inconsistency with the request |
| **Human review** | A responsible person accepts decisions that require product, security or operational judgment |

Choose checks before execution when possible. Verification is strongest when its success condition comes from the task and repository rather than from the agent that wrote the code.

## A failed check is feedback

To repair failed CI checks automatically, enable **Fix pull request checks** and select the checks and maximum attempts. This optional automation waits for checks, starts a correction on failure, and pauses automatic fixes at the attempt limit. A timeout records an error rather than proof of success. Without it, inspect the failure and request a correction through your review process.

The default **Address PR feedback** handler responds to human comments and reviews that mention `@superplaneagent`, and to bot feedback under the onboarding settings. Check the handler's filters if a comment does not start a run. A correction updates the pull request; it does not guarantee that the requested behavior or all checks pass.

This creates a bounded correction loop:

<div class="factory-execution-flow not-content" role="list" aria-label="Verification correction loop">
  <span role="listitem">Run the required checks</span>
  <span role="listitem">Capture the failure</span>
  <span role="listitem">Return focused feedback</span>
  <span role="listitem">Recheck the new result</span>
</div>

Limit the loop. Repeated failure can signal a poorly scoped task, a missing dependency or a decision the agent cannot make. At that point the useful action is to ask for attention rather than spend another attempt on the same assumption.

## Separate run health from result quality

A workflow step can execute successfully and still produce an unacceptable result. It can also encounter a temporary API failure before the code is evaluated. Keep these cases distinct:

- **Execution failure:** The component could not complete because an external service, credential or runtime failed.
- **Verification failure:** The component ran and the change did not meet a required condition.

The first may need an operational retry. The second should change the code or the task. Keeping both visible makes recovery faster and reporting more honest.

## Know when to ask a person

Human attention is appropriate when the answer depends on judgment rather than computation. Examples include accepting a user-facing tradeoff, approving a sensitive dependency, interpreting an ambiguous requirement or deciding whether a broader refactor belongs in scope.

## Exit criteria

Review the diff, check results and remaining decisions before merging. In the default workflow, the task stays in Verify while its pull request is open, even when checks pass. The PR Closure automation records completion after merge and a rejected outcome after closure without merge. For tasks with multiple attached pull requests, it waits until all are merged or closed.

Additional approval gates and completion boundaries require configuration. Read [Done](/fundamentals/done) to distinguish the recorded task outcome from verification evidence.
